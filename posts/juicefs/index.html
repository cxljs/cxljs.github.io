分布式文件系统的发展

Google GFS 是分布式文件系统发展的里程碑，Meta 和 Data 分离的架构影响了后来的分布式系统设计。随后的 HDFS 是大数据时代最重要的存储系统之一，现在分布式文件系统最流行的2种接口协议是 POSIX 和 HDFS。

随着云原生和对象存储的发展，数据系统的设计趋势是把数据放到对象存储，比如 Neon, AutoMQ, JuiceFS.

LLM 训练和推理对分布式文件系统的要求和大数据场景不同，LLM 训练过程需要读取大量小文件，checkpoint 会写入大文件，部署推理服务也需要读写大文件，所以文件系统需要同时在大小文件都有好的性能，小文件有更多元数据，对元数据服务要求更高。分布式文件系统还有一个热点是 GPU Direct FS。

分布式文件系统的挑战

文件系统的元数据组成一棵树，分布式文件系统的挑战之一是怎么存储和高性能读写树。

常见思路：

  1. 整个树存储在单个节点（主备模式做故障容忍），缺点是单节点吞吐量和容量有限，可能会成为系统瓶颈
  2. 设计一个可扩展的存储树的系统，把树划分存储到多个节点，百度的文件系统的元数据系统就是这样设计，发过论文
  3. 转化成 KV/Table 数据模型存储在 KV/RDB
  4. 不采用 Meta + Data 架构，把 Meta 和 Data 混合存储

JuiceFS

JuiceFS 是一个基于对象存储的文件系统，被阶跃、小米等公司使用，这篇文章主要是了解 JuiceFS 的设计。

JuiceFS 是经典的 client-meta-data 架构，采用上面的第3种思路存储元数据，支持 TiKV/MySQL/Etcd/Redis 等多种系统作为 Meta Service，数据放在对象存储，JuiceFS 本身是一个 client 层。

架构：

app        fuse lib  -->  juicefs --> meta service
 |            |             |
 |            |         object store --> object storage service
syscall    /dev/fuse        |
 |            |          local cache
vfs    -->   fuse

使用：

# 创建一个新文件系统
juicefs format redis://127.0.0.1:6379/1 myjfs

# 挂载
juicefs mount redis://127.0.0.1:6379/1 /tmp/jfs

文件存储模型

如果一个文件作为一个对象去存储，修改文件有严重的写放大，所以需要把文件划分成多个对象去存储。

为此 JuiceFS 设计了 file-chunk-slice-block 模型：

  • 文件逻辑上划分成多个 chunk，chunk size = 64MB
  • 对 chunk 的每次写为一个 slice，slice = (chunk id, offset, size, data)，多次写可能有重叠，所以还要维护 slice 顺序，以最新的为准，跨 chunk 的写会分成多个 slice
  • slice 存储到对象存储时被划分成多个 block (block size = 4MB) 并发写入，所以对象存储里的对象是一个个 <= 4MB 的 block

block 为存储的单位 vs. slice 为存储单位：

  • pros.:
    • 方便并发上传，slice 为单位也可以用 multipart 方式上传，但是有些对象存储不支持 multipart
    • 方便 slice GC，juicefs 为了避免写放大，修改文件时，juicefs 不是“下载对象->修改->重传”，而是直接上传新对象，旧对象直到没有引用时删除，以 block 为单位，能更快删除旧数据
    • block size 固定，本地 object cache 的实现更加简洁
  • cons.:
    • 更多元数据，对 meta service 压力更大

对象名：${fsname}/chunks/{slice_id/1e6}/{slice_id/1e3}/${basename}:

  • fsname: 用户创建文件系统时定义的文件系统名
  • hash: 避免单桶成为热点
  • basename: 格式是 ${slice_id}_${block_index}_${block_size}，block_index 是 block 在 slice 的序号，范围 [0,16)

多个写重叠会有过期 slice -> 有过期 block，所以需要有删除策略，slices 压缩等设计。

上面说每次写是一个 slice，实际上由于有 local data cache，JuiceFS 会做一些优化，比如一次写后，slice 还没有上传到对象存储，此时有新的写操作和它重叠或连续，会直接修改它，不创建新 slice。

元数据存储模型

JuiceFS 需要维护的元数据：

  • 系统元数据
  • 各种计数值：下个可用的 inode id / slice id / session id / &c
  • session: client id, client info 和超时时间
  • inode attr：type, size, nlink, uid, parent inode id, &c
  • file inode data (chunks): (inode id, chunk index) -> []sliceMeta
  • dir inode data：(dir inode id, child inode name) -> (child inode type, child inode id)
  • plock: (inode, session id, owner) -> []plock record
  • …

JuiceFS 需要设计合理的数据模型，把元数据放到 TiKV/MySQL/Redis 等系统。

在 Redis 的数据模型：

  • 系统元数据：string KV ：setting -> json string
  • 各种计数值：string KV ：nextInode -> num, nextSliceId -> num, &c
  • session
    • session timeout: allSessions -> a sorted set {member: client id, score: timeout timestamp}
    • session info: sessionInfos -> a hash table {client id -> json string}
  • inode attr: string KV: i${inode_id} -> 二进制编码的 attr struct
  • chunk: c${inode_id}_{chunk_index} -> a list {二进制编码的 sliceMeta struct}
  • dir: d${inode_id} -> a hash table {child inode name -> 二进制编码的 (inode_type, inode_id)}
  • …

用只有 KV API 的系统作为 Meta Service 时，JuiceFS 的做法是 string KV 不变，hash table 等数据结构把 key 和 field 拼接成一个 key：

  • 系统元数据：setting -> json string
  • session
    • SE${client_id} -> timeout timestamp
    • SI${client_id} -> json string
  • inode attr: A${inode_id}I -> 二进制编码的 attr struct
  • chunk: A${inode_id}C${chunk_index} -> 二进制编码的 sliceMeta array
  • dir: A${inode_id}D${name} -> 二进制编码的 (inode_type, inode_id)
  • …

key 的具体拼接细节没有保持一致，但无伤大雅。

用数据库作为 Meta Service，元数据分成多个表存放。

以读文件数据为例，流程：

  1. root inode id = 1, 沿着文件路径找到 inode_id, file size(in attr struct)
  2. 计算要读的 chunk_index, 获取 []sliceMeta
  3. 计算要读的位置在哪些 slices 以及在 slice 内的 index，${slice_id}_${block_index}_${block_size} 读取 block，拼接数据

VFS

vfs 从文件系统的视角，实现文件系统语义，维护需要的元数据，client 租约等。

写文件时，数据和元数据在两个系统，JuiceFS 的设计是先写数据、再写元数据，以元数据成功写到 Meta Service 作为 commit point.

文件系统语义，Reader 和 Writer 的实现有很多细节，具体看代码。

Meta Service

要求 Meta Service 具备事务能力，Redis 的话是使用 watch + multi/exec 实现乐观锁。

Chunk Store

chunk store API 的设计很好，不需要理解 file-chunk-slice-block 模型，从 chunk store 的视角，它负责维护多条线段，每条线段会作为一个对象上传到对象存储：

  • 用户写就是告诉它在哪条线段的哪个位置写入数据，线段存储在内存，由用户自己决定上传到对象存储的时机
  • 用户读会从本地 cache 找，找不到再从对象存储读

实现主要考虑：

  • 对象存储到磁盘的模式，JuiceFS 采用 file-per-block, 也就是每个对象和他的 crc 作为一个文件
  • 预读策略
  • 上传和下载对象的并发限制

我没有太详细地看代码，只看了大概，然后假设我来设计 chunk store 我会怎么设计，再和 JuiceFS 的设计对比，主要区别：file-per-block 的模式，当缓存大量对象时，会在本地产生大量文件，我会采用 n 个大文件，每个大文件切分成多个部分，每个部分放一个对象，并用 bitmap 维护每个文件的空闲部分。
